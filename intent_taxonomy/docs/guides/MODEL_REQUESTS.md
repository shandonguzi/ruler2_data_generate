# 模型额外参数、思考开关与 Token 统计

## 配置额外请求参数

在桌面页面「模型配置」中，对话模型和 Embedding 都有「额外请求参数」。点击「添加参数」，输入 key 和 JSON value；可删除参数，保存后同步写入 config/config.yaml。字符串需加双引号，布尔值和数字不加引号。

例如：

| Key | Value |
|---|---|
| top_k | `20` |
| chat_template_kwargs | `{"enable_thinking":false}` |

这些字段通过 OpenAI Python SDK 的 `extra_body` 传入，合并到 HTTP 请求体顶层；不会发送一个额外嵌套的 `extra_body` 字段。模型、输入内容和流式返回由程序管理，不能通过额外参数覆盖 model、messages、input、stream。未知或不支持的服务参数会正常报错，不会悄悄丢弃。

## 思考开关

对话模型提供三种模式：

- 服务默认 / 使用自定义参数：不注入开关值，原样使用 key/value 参数。
- 开启思考：向指定参数路径写入布尔值 true。
- 关闭思考：向指定参数路径写入布尔值 false。

默认路径为 `chat_template_kwargs.enable_thinking`，对应 Qwen/vLLM 的请求方式。路径可修改，例如某些服务使用顶层 `enable_thinking`。开关会覆盖该路径已有的同名 value，保留其他参数。

若服务要求字符串或其他结构，例如 `thinking: {"type":"enabled"}`，使用「服务默认 / 使用自定义参数」，直接通过 key/value 配置。不同服务的思考参数不统一，支持方式以服务端为准。[Qwen/vLLM 官方说明](https://qwen.readthedocs.io/en/latest/deployment/vllm.html#thinking-non-thinking-modes)

配置示例：

```yaml
llm:
  thinking_mode: "off"
  thinking_parameter: "chat_template_kwargs.enable_thinking"
  extra_body:
    top_k: 20
```

「检测连接」使用尚未保存的表单内容，也包含思考开关和额外参数；实际任务使用保存后的配置。Embedding 不注入思考开关，但支持自己的额外参数，其参数变化会影响向量缓存身份。

## 用量统计口径

程序读取服务端 response.usage，不按字符长度估算 Token：

- prompt_tokens：输入 Token；Embedding 的输入也单独按模型统计。
- completion_tokens：对话输出 Token；Embedding 记为 0。
- total_tokens：服务端总量，缺失时仅在输入和输出均已知时相加。
- cached_tokens：服务端单独返回的缓存输入明细，已包含在输入中。
- reasoning_tokens：服务端单独返回的思考明细，已包含在输出中，不额外叠加。

服务端未上报 usage 或字段不完整时，会记录「用量未知」，不会把它当作零消耗。没有提供思考或缓存明细时，页面不伪造这些明细。输出 Token 的口径包含模型生成的隐藏内容，不能只按可见回答的长度判断。[OpenAI 官方 Token 统计说明](https://developers.openai.com/api/docs/guides/token-counting)

每次重试的已返回响应都会计入，包括最终 JSON 校验失败的响应；API 异常若附带 usage 也会保留。失败但没有用量信息的请求记为未知。本地缓存命中不产生模型请求。SDK 隐式重试已关闭，重试由应用控制，以记录每次尝试。

统计位置：

- 「运行任务」实时显示当前任务的已报告输入、输出、总量和未知请求数。
- 模型检测显示本次请求的用量；未返回 usage 时明确提示。
- 工作空间选择流程后显示本版本用量；中间结果预览中可选择「Token用量」表，查看对话与 Embedding 各模型的统计。
- 阶段 JSON、完整结果和流程清单包含 token_usage；工作簿包含「Token用量」sheet。

每个派生运行只统计本次产生的请求，阶段快照累计到该阶段，不重复计入父版本成本。手工整理层级不调用模型，新版本统计为零次请求。历史版本无法补算没有记录的服务端用量。

取消或进程异常退出时，正在执行但没有返回的请求用量可能无法取得；已报告总量不等同于最终账单。统计事件不包含 API Key、用户原句或模型回答正文。

## 请求记录的读取与索引

「运行任务」与「分类与迭代」共用请求记录读取逻辑。点击查看不会调用模型，也不重新计算向量。请求日志写入时，程序同步提取请求时间、所属阶段、父子簇关系以及输入筛选信息，保存到同目录的 `requests.jsonl.sqlite3` 索引；原始输入输出仍保存在 `requests.jsonl` 中。

页面请求时间按北京时间（Asia/Shanghai，UTC+8）显示，不依赖浏览器所在时区；这是显示转换，不会更改原始日志时间。列表按请求开始时间倒序，每页只读取 10 条原始记录。父子簇视图使用索引中的关系摘要，首次整理后持久化缓存；没有新请求时直接复用，新记录写入后刷新缓存。父子簇展开时再分页读取对应簇的请求正文。

历史日志在首次查看时自动补建索引，因此第一次打开仍可能稍慢。后续只增量索引新增记录，服务重启后也可复用；删除索引不会丢失原始记录，下次查看会重建。删除流程时会一并清理其请求日志和索引。

## 续跑中的请求回放

显式指定 --resume-trace 时，仅对旧日志中的成功对话响应按完整请求参数匹配并重新校验；命中记录标记 replayed，不新增服务调用或 Token。失败、缺少 parsed 或不符合当前响应结构的记录不复用。Embedding 不使用该回放器，仍使用向量缓存。

归并阶段还可在任何向量计算前按完成身份直接跳过，不能把阶段被执行或进度显示完成当作发生模型调用。整轮完成复用与逐对缓存的区别见 [继续迭代与复用指南](CONTINUATION_AND_REUSE.md)。

### 多 LLM 随机请求池

在模型配置页展开“多个 LLM · 随机请求”，添加额外服务地址、模型名和 API Key 环境变量名，保存后写入 `llm.endpoints`。原对话模型也参与池中，每次对话请求随机选一个端点，各阶段共用；同次调用重试优先选择尚未尝试的端点，总尝试次数仍受 `llm.max_retries` 限制。所有端点均失败后返回失败，不额外无限重试。

额外端点默认继承主模型温度、Token 上限和额外请求参数，凭据不继承主模型明文 Key。模型接口必须支持同一套 JSON 任务协议。每条请求记录显示实际模型及 base_url，用量按实际服务分别统计。已成功的审核缓存会复用；请求池改变时相关审核身份失效。Embedding 不参与该池。修改配置影响后续启动任务，运行中的任务保持原配置。


### 服务启动与历史日志

启动只恢复历史任务状态、进度与用量摘要；首次查看具体任务时再从日志尾部读取最多2,000行、2 MiB；接口每次最多返回最近500条，跳过数量会明确提示，页面内容限制为最近256,000字符。“下载完整日志”保留全量JSONL访问，不删除原始日志。已结束且未变化的历史状态不重复写盘，上次中断的任务仍会记录重启后的失败状态。Windows启动脚本通过模块存在性检查判断是否需要安装依赖，服务进程负责实际导入。
